# A&M Logistics website

The customer site (`index.html`), customer app (`/user-app`), rider registration (`/rider`), rider app (`/rider-app`), and admin pages (`/admin`) are separate pages. Express serves them from the same host and provides the shared API, so customer accounts, delivery requests, rider reviews, assignments, and notifications work across browsers and devices.

The production web app is served from Render at `https://a-mlogistic.onrender.com`. The frontend API client uses that URL; the server also hosts the frontend, so use the Render URL for the public site. Admin, rider registration, customer app, and rider app are available at `/admin`, `/rider`, `/user-app`, and `/rider-app`. Their `.html` URLs and trailing-slash versions redirect to these clean paths.

## Run locally on Windows

1. Install Node.js 22.13 or newer.
2. In PowerShell, run `npm.cmd install`.
3. Copy `.env.example` to `.env`, set a private admin email and a unique password of at least 12 characters, and configure the Brevo API key and a verified sender email.
4. Run `npm.cmd start`.
5. Open `http://localhost:3000` in a browser. Do not open the HTML files directly or use a static-only preview server; the API must be running.

In development, the server creates and updates `data\users.json`, `data\riders.json`, `data\orders.json`, `data\notifications.json`, and `data\sessions.json`. The first server startup imports existing records from `data\ao-logistics.sqlite` when that database exists; the SQLite file is left in place as a backup. Customer and rider passwords are hashed on the server, and package photos are stored with their orders.

## Supabase production database

Production, including the app running on Render, uses Supabase PostgreSQL. The app will not silently fall back to local JSON files on Render, even if `NODE_ENV` is missing. In Supabase, open **SQL Editor**, paste and run [`supabase-schema.sql`](./supabase-schema.sql) on initial setup and again when deploying schema updates (including weekly payouts), then set these values in the server host's private environment settings:

- `SUPABASE_URL`: the project's URL from Supabase **Project Settings → API**.
- `SUPABASE_SERVICE_ROLE_KEY`: the project's service-role (secret) key from Supabase **Project Settings → API Keys**. Keep this server-side only; never put it in browser code or commit it.
- `NODE_ENV=production`.
- `ALLOWED_ORIGINS=https://mar47362626-eng.github.io,https://a-mlogistic.netlify.app` so hosted frontends are permitted to call the backend. These deployed origins are also included in the app's defaults; same-host Render requests are allowed automatically.
- The public Render service URL is configured in `api-client.js` as `window.API_BASE_URL` before publishing the static GitHub Pages frontend; this is public configuration, not a secret.
- Bank transfer details can be entered and saved from the **Customer transfer account** form at the top of the admin Orders page. Customers see the saved bank name, account name, account number, confirmed amount, and order reference in their payment instructions. `BANK_NAME`, `BANK_ACCOUNT_NAME`, and `BANK_ACCOUNT_NUMBER` remain optional Render environment fallbacks.
- `DELIVERY_BASE_FEE_NGN` and `DELIVERY_RATE_PER_KM_NGN`: optional estimate settings; defaults are `2500` and `1000`.
- Rider earnings are 5% of the amount the customer reports paying and A&M verifies. Earnings are recorded when delivery is completed and rounded to the nearest whole naira. Riders can request unclaimed earnings for completed weeks from the rider dashboard; admins review requests in the Delivered workspace and mark them paid or declined.

The server requires valid Supabase credentials in production and does not silently fall back to local JSON files. The Supabase URL must use HTTPS because the server sends its service-role key with database requests. Production also requires an administrator to be provisioned before the server starts: set the private `ADMIN_EMAIL` and `ADMIN_PASSWORD` environment variables, or retain an existing admin account. The public admin-registration endpoint only allows a signed-in administrator to add another admin; never enable public first-admin registration. Local development can continue using JSON storage without Supabase credentials. Existing local JSON/SQLite data is not copied automatically; migrate existing records before switching production traffic if you need to retain them. Do not put `.env` or any service-role key in GitHub.

If Render reports `permission denied for table app_records`, rerun `supabase-schema.sql` in the matching Supabase project's SQL Editor and confirm that Render's `SUPABASE_SERVICE_ROLE_KEY` is that same project's service-role secret key, not its anon/publishable key. The schema grants table access to `service_role`.

## Configure admin-set delivery fees and bank transfer

Set the business receiving account in the admin **Customer transfer account** form before accepting transfers. The settings are stored with the admin account records and are available to customers across devices; the matching environment variables remain an optional fallback. Google Maps, a Maps API key, and a Google billing account are not needed.

Customers enter pickup and delivery addresses, then choose **Calculate route and fee**. The server geocodes both addresses with OpenStreetMap Nominatim and calculates driving distance with the public OSRM routing service; customers do not enter kilometres, and no Google Maps key or card is needed. The matched places and distance are shown with the estimate. Address lookup sends the entered addresses to OpenStreetMap. These public services have usage limits and no uptime guarantee; if an address cannot be matched or routing is unavailable, the customer must try a more complete address or try again later. The server issues a short-lived, signed route quote for the customer and addresses so order submission can validate the estimate without repeating external map lookups. By default, the estimate is NGN 2,500 plus NGN 1,000 for each started kilometre (for example, 2.4 km is estimated as NGN 5,500). Configure `DELIVERY_BASE_FEE_NGN` and `DELIVERY_RATE_PER_KM_NGN` in Render to change the estimate formula. The bank account saved by the admin is shown in the request form before the customer submits. The customer transfers the estimated fee, enters the transaction reference, checks **I have paid**, and submits the request in one step; the request and payment reference are then available to admins in the order queue. Customer and admin email notifications are sent in the background so a slow email provider cannot hold up the order confirmation. The estimate can differ from the final fee, so A&M reviews the route and contacts the customer if an adjustment is needed. An admin must compare the reference and received amount with the bank statement before choosing **Verify payment**. Submitting a reference does not itself prove that funds arrived; rider pickup verification remains unavailable until the admin confirms payment.

After creating the Render service, set its build command to `npm ci`, start command to `npm start`, and leave **Root Directory** empty. Configure the server environment variables above in Render's dashboard. The Netlify site routes `/api/*` through a same-origin proxy configured in `netlify.toml`, and `api-client.js` uses the Netlify origin automatically. This keeps login cookies first-party in the browser and avoids third-party-cookie blocking. For GitHub Pages, `api-client.js` continues to use the Render API URL directly; use the matching Pages origin in `ALLOWED_ORIGINS` and do not include the repository path. Production auth cookies require HTTPS.

## Android apps

The Android project in `android-app/` builds two separate apps: **A&M Logistics** opens the customer portal (`https://a-mlogistic.netlify.app/user-app`), and **A&M Rider** opens the rider portal (`https://a-mlogistic.netlify.app/rider-app`). They install independently and keep their respective portal features available in the app. The customer portal does not display an app download link.

To build and publish downloadable APKs, push a version tag such as `android-v1.0.0`. The `Android apps` GitHub Actions workflow builds debug-signed customer and rider APKs and attaches both to that release as `ao-logistics-customer.apk` and `ao-logistics-rider.apk`. The workflow requires no signing secrets. These APKs are suitable for direct Android installation/testing, not for publishing to Google Play. GitHub's runner creates a debug signing key for each build, so installing a later APK may require uninstalling the earlier APK of the same app first. Play Store distribution and seamless app updates require a separately configured release signing key, which must be stored as a GitHub Actions secret and never committed.

For a local build, open `android-app/` in Android Studio with JDK 17 and Android SDK 35 installed, or run `gradle assembleCustomerDebug assembleRiderDebug` from that directory. The generated APKs are at `android-app/app/build/outputs/apk/customer/debug/app-customer-debug.apk` and `android-app/app/build/outputs/apk/rider/debug/app-rider-debug.apk`.

### Publishing on Google Play

The release APKs above are debug builds and cannot be submitted to Google Play. Create a Play Console developer account, configure a private release upload key and release signing in Gradle, then build signed Android App Bundles with `gradle bundleCustomerRelease bundleRiderRelease`. Keep the keystore and passwords outside the repository and back them up securely; enroll each app in Play App Signing. Create separate Play Console listings for the customer and rider apps, complete their store listings, privacy/Data safety declarations, content ratings, and testing/review steps, and upload each app's `.aab` to its own listing.

Before submission, update the Android build to meet Google's current target API requirement. As of August 31, 2026, new apps and updates must target Android 16 (API level 36) or higher. This project currently targets API 34, so it is not Play-ready yet. Google may also reject apps that provide too little functionality beyond a website; review its [target API requirements](https://support.google.com/googleplay/android-developer/answer/11926878) and current app quality policies before submitting.

## iOS apps

The iOS project in `ios-app/` contains two separate Xcode targets: **A&M Logistics** opens the customer portal and **A&M Rider** opens the rider portal. Open `ios-app/AoLogistics.xcodeproj` on a Mac with Xcode, select either the `Customer` or `Rider` scheme, choose an iPhone simulator or connected device, and run the app. Before installing on a physical device or archiving for the App Store, configure your Apple Developer team and the matching app's signing settings in Xcode.

Publishing requires an Apple Developer Program account, App Store Connect records for both distinct bundle IDs, store screenshots and privacy details, and an App Store review for each app. Apple may reject apps that only wrap a website, so review its minimum-functionality requirements and add native value if needed before submitting. Building, signing, and uploading iOS apps requires macOS and Xcode.

## Main workflows

- Customers register and receive a welcome email, then sign in and create delivery requests with pickup and delivery contact email addresses. The customer and configured admin accounts receive an email when a request is placed.
- Delivery requests accept common photo formats (JPEG, PNG, WebP, GIF, BMP, AVIF, HEIC/HEIF, and TIFF) up to 5 MB.
- Riders apply with an account password and receive an application email. When an administrator confirms an order with an approved rider assigned, the rider receives the assignment by email.
- Administrators receive email alerts for new delivery requests, rider applications, completed deliveries, and rider payout requests. Riders receive a completion email with their calculated earnings; admins can review the delivered item, rider, earnings, and payout request in the Delivered workspace.
- Order emails to customers, configured admins, the assigned rider, and pickup/delivery contacts embed the uploaded package photo directly in the message body as a CID inline image. This includes new-request, rider-assignment, handoff-code, and status-update emails.
- Riders request a short-lived pickup code for the pickup email and a separate delivery code for the delivery email. The rider must verify both codes to advance the order through collection and delivery. Customers receive an email when an order status changes; when the rider verifies pickup, the delivery contact also receives a pickup/on-the-way update.
- Administrators sign in at `admin-login.html`, see recent customer and rider registrations in Notifications, approve or decline rider applications, review driving licence IDs, confirm orders with a rider assigned, review customers and completed deliveries, and send account notifications by email and to recipient dashboards.
- Riders request a weekly payout from the rider dashboard for an available completed week. Each completed delivery can only be included in one active payout request; admins can mark a request paid or decline it, and the rider receives an email update.
- New customer orders show an estimate based on the driving route calculated from the pickup and delivery addresses. The saved receiving account is displayed before the customer submits the request. The customer pays the estimate and submits the request together with the bank transaction reference (not a receipt upload); admins receive the order and transfer reference in the admin order list and email. An admin checks the bank transfer, verifies it, reviews the route and final fee, and assigns an approved rider before confirming the order. Riders cannot request a pickup code until payment is verified.

Brevo mail uses its transactional email API. Set `BREVO_API_KEY` to a current **transactional API key** (not an SMTP key), `BREVO_SENDER_EMAIL` to a sender verified in Brevo, and optionally `BREVO_SENDER_NAME`; `ADMIN_EMAIL` receives new order notices. For Render, add secrets in the Render service's **Environment** settings, not in frontend code. If Brevo IP authorization is enabled, allow the outbound IP addresses for this Render service (from Render service settings); a local computer IP is not the Render IP. On an API `401`/`403`, check the API key and Brevo's response detail in the Render logs to distinguish a rejected key from an unauthorized server IP. Order emails can embed package photos inline when `BREVO_SMTP_LOGIN` and `BREVO_SMTP_KEY` are set to the separate SMTP credentials from Brevo; `BREVO_SMTP_PORT` accepts 465, 587, or 2525 (default 587). If SMTP is not configured or fails, the app sends through the transactional API and includes the photo as a regular attachment instead. Non-order emails use the transactional API directly. Handoff codes are sent and saved separately from the subsequent status-photo email, so a failure to send a status email does not invalidate a handoff code. The app reports notification failures separately. Never put credentials in browser code or commit a populated `.env` file.

For production, run the server behind HTTPS, set `NODE_ENV=production`, use a strong private admin password, and configure Supabase. Package photo bytes are saved with order records in the database.
